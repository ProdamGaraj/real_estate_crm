# Назначение и условия применения программы

## Назначение

Программа автоматизирует продажи объектов недвижимости. Перечень функций — в документе «Описание автоматизированных функций»; коды функций (ОРГ-01, СДЕ-04 и т.д.) рекомендуется указывать в задачах и сообщениях коммитов.

## Условия применения

Среда исполнения — по документу «Руководство системного программиста». Среда разработки:

- Python 3.12 и виртуальное окружение в каталоге `backend/.venv` (`pip install -r requirements.txt`);
- Node.js 20 и зависимости клиентской части (`npm ci` в каталоге `frontend-new`);
- для локального запуска серверной части без Docker — переменная `USE_SQLITE=True` (БД SQLite) и локальный Redis либо замена кэша (см. 2.9);
- для запуска комплекса в режиме разработки — `docker compose -f docker-compose.dev.yml up` (горячая перезагрузка клиентской части через nginx в режиме `DEV_MODE`).

## Разграничение доступа

Разрешение — запись `permissions.Permission` с полями `action`, `resource`, `scope`. Роль (`permissions.Role`) — набор разрешений; профиль пользователя (`permissions.UserProfile`) — набор ролей, компания и отдел. Проверки выполняются функциями модуля `permissions/backends.py`:

- `can_user_perform_action(user, action, resource_type, obj=None, scope=None)` — может ли пользователь выполнить действие; с `obj` дополнительно проверяется, входит ли объект в область разрешения;
- `get_filtered_queryset(user, queryset, resource_type, max_scope=None)` — отбор записей по наибольшей области видимости пользователя для ресурса;
- `get_user_max_scope(user, resource_type)` — наибольшая область пользователя.

На уровне программного интерфейса применяются классы `permissions/permissions.py`, наследники `BaseResourcePermission` с атрибутом `resource_type`: метод HTTP отображается в действие (`GET` — `VIEW`, `POST` — `ADD`, `PUT` и `PATCH` — `EDIT`, `DELETE` — `DELETE`).

Правила:

1. каждое представление, выдающее записи, обязано отбирать их через `get_filtered_queryset`; проверка только класса разрешения не ограничивает данные областью видимости;
2. суперпользователь и профиль с признаком `is_system_admin` проходят все проверки;
3. интерфейс скрывает недоступное (`frontend-new/src/utils/permissions.ts`: `hasPermission`, `isSystemAdmin`, `getMaxScope`), но сервер проверяет всё самостоятельно.

### Добавление нового ресурса

1. Добавить код в `Permission.Resource` (`permissions/models.py`) и создать миграцию.
2. Выполнить `python manage.py init_permissions` — будут созданы разрешения по всем действиям и областям; для включения в типовые роли изменить `init_permissions.py` и выполнить с `--sync-roles`.
3. Создать класс разрешения — наследник `BaseResourcePermission` с `resource_type`.
4. В представлениях использовать этот класс и `get_filtered_queryset`.
5. В клиентской части добавить код в тип `ResourceType` (`utils/permissions.ts`), перевод `resources.<КОД>` во все три файла локализации и, при необходимости, пункт меню (`layouts/RootLayout.tsx`) или вкладку настроек (`utils/settingsTabs.ts`).

## Изоляция компаний

1. Каждая бизнес-модель и модель справочника имеет поле `company`.
2. При создании записи компания берётся из профиля пользователя (`request.user.profile.company`), а не из входных данных.
3. Ссылки на связанные записи во входных данных (клиент, объект, счёт получателя, тип платежа, ответственный) проверяются в сериализаторе на принадлежность компании пользователя; ссылка на запись другой компании — ошибка проверки.
4. Уникальность значений, видимых пользователю (адрес электронной почты клиента, номер договора, название записи справочника), задаётся в пределах компании (`unique_together` с `company`).
5. Справочники подключают `CompanyScopedReferenceMixin` (`permissions/reference_scope.py`): выдаются записи своей компании и общесистемные (`company IS NULL`); общесистемные создаёт и изменяет только администратор.
6. Записи, создаваемые системой автоматически (журналы, встречи при регистрации клиента, клиенты из публичного API), также получают компанию.

Команда `check_company_isolation` показывает записи без компании.

## Мягкое удаление

Модели заявок и встреч имеют поля `is_deleted`, `deleted_at`, `deleted_by` и методы `soft_delete(user)` и `restore()`. Представления подключают `SoftDeleteMixin` (`apps/crm/views.py`): `perform_destroy` помечает запись и пишет журнал, `filter_deleted` исключает удалённые записи, если не передан параметр `include_deleted=true`. Восстановление — маршруты `…/<id>/restore/`. Все выборки для отчётов и сводных таблиц обязаны исключать удалённые записи.

## Журналы изменений

Для журналируемых моделей существует модель журнала (`ApplicationLog`, `ClientLog`, `MeetingLog`, `DealLog`, `PaymentLog`, `BuildingLog`, `DiscountLog`, `TaskLog`) с полями записи, пользователя, времени и текста действия. Запись журнала создаётся в представлении при каждом значимом изменении; для полей с изменёнными значениями используется формулировка «Поле '…' изменено с '…' на '…'», которую разбирает компонент клиентской части `HumanizedLog`. Изменение этой формулировки требует согласованного изменения компонента.

## Транзакции и конкурентный доступ

Изменения нескольких записей выполняются в `transaction.atomic()`. Создание брони блокирует запись объекта (`select_for_update`) и повторно проверяет её статус и наличие блокирующих сделок внутри транзакции — это исключает двойную бронь. Этот же приём применяется при любых изменениях статуса объекта.

## Выдача файлов

Поля файлов сериализуются функцией `build_media_url(file_field)` (`real_estate_project/media_access.py`): для общедоступных каталогов (`projects`, `buildings`, `layouts`, `avatars`) возвращается прямая ссылка, для остальных — ссылка с подписью и сроком действия (`sign_media_path`). Маршрут `/media/<путь>` (`serve_media`) проверяет подпись и при `MEDIA_USE_ACCEL_REDIRECT=True` возвращает заголовок `X-Accel-Redirect` на `/protected-media/<путь>`, иначе отдаёт файл сам. Новый каталог файлов должен быть подключён в сервисы `backend` и `nginx` файла `docker-compose.yml`.

## Постраничная выдача и ошибки

Списки выдаются целиком, если в запросе нет параметра `page`; при его наличии — постранично (`page_size` по умолчанию 50, не более 500; класс `OptionalPageNumberPagination`). Ответ при постраничной выдаче содержит `count`, `next`, `previous`, `results`.

Отказ в операции возвращается с кодом 400 (403, 404) и телом вида `{"error": "текст"}` либо `{"<поле>": ["текст"]}`. Текст должен объяснять пользователю причину и способ исправления. Клиентская часть извлекает его функцией `extractApiError` (`utils/apiError.ts`); новые формы должны использовать её, а не общее сообщение.

## Кэш и Redis

Кэш Django (`CACHES`) размещён в Redis: в нём хранятся счётчики ограничения частоты запросов, неудачных попыток входа и отметки последнего пересчёта просрочки. В тестах кэш заменяется на `LocMemCache` декоратором `override_settings` — без этого тесты обращаются к Redis.

## Локализация клиентской части

1. Загружаются только файлы `src/i18n/locales/ru.json`, `en.json`, `uz.json`. Каталоги `locales/{ru,en,uz}/*.json` — устаревший результат сценария `scripts/split-locales.cjs`, в приложение не подключаются; ключи с префиксами вида `permissions.*`, `buildings.*`, рассчитанные на них, не работают.
2. Любая надпись интерфейса выводится через `t('ключ')`; ключ должен существовать во всех трёх файлах. Второй аргумент `t('ключ', 'текст')` не использовать: он скрывает отсутствие перевода.
3. Коды классификаторов переводятся функциями `utils/translations.ts` (`translateDealStatus`, `translateResource` и др.); новое значение перечисления сервера требует перевода в ветках `statuses.*` или `resources.*` всех языков.
4. Таблицы MUI DataGrid выводятся через `components/common/LocalizedDataGrid.tsx`: для русского языка используется официальная локаль `ruRU`, для узбекского — собственный набор с именами ключей версии 8.
5. Сообщения сервера и тексты журналов формируются на русском языке.
6. Язык, определённый по браузеру (`ru-RU`), приводится к коду языка (`ru`) параметром `convertDetectedLanguage` в `i18n/config.ts`: тема, таблицы и форматы дат сравнивают язык с кодом.

7. Денежные суммы и числа выводятся функциями `formatMoney` и `formatNumber` (`utils/currency.ts`): разряды разделяются неразрывным пробелом на всех языках, десятичный разделитель — по языку. `toLocaleString()` для сумм не используется: в английском интерфейсе он ставит запятые. Копирование отформатированной суммы со страницы или из поля отдаёт число без пробелов и кода валюты (`installNumberCopyHandler`, подключается в `main.tsx`).

> Примечание – В клиентской части включён параметр `verbatimModuleSyntax`: типы импортируются как типы (`import type { … }` или `{ type … }`). Тип, импортированный как значение, не мешает сборке, но в режиме разработки (`npm run dev`) приложение не запускается — страница остаётся пустой с ошибкой «does not provide an export named …» в консоли.

## Валюты и курсы

Пересчёт сумм между валютами выполняется только функциями модуля `apps/finances/currency.py`: `cross_rate` (кросс-курс на дату через сум), `convert` (сумма на дату), класс `Converter` (приведение множества сумм к одной валюте без обращения к ЦБ, с перечнем валют без курса — для отчётов и дашборда). Кросс-курс в вычислениях не округляется: у пары сум → доллар он порядка 0,00008, и округление до 8 знаков давало ошибку до нескольких долларов на договорах в миллиарды сумов. Для записи курса в сделку или платёж используется `stored_rate` (12 знаков). Итоговая сумма округляется функцией `money` до 0,01 по правилу «половина вверх».

Курс хранится в модели `ExchangeRate` как число сумов за единицу валюты; запись без компании — курс ЦБ, с компанией — ручной курс. Валюта сделок и поддерживаемые валюты компании возвращаются функциями `company_base_currency` и `supported_currencies`. Отсутствие курса сообщается исключением `RateUnavailable`, текст которого показывается пользователю.

## Регламентные задания

Задания оформлены командами управления (`management/commands`) и запускаются контейнером `scheduler` раз в час. Новое задание добавляется командой управления и строкой в разделе `command` сервиса `scheduler`. Задание должно быть идемпотентным: повторный запуск не меняет уже обработанные записи.

# Обращение к программе

## Программный интерфейс для клиентского приложения

Все маршруты имеют префикс `/api/`. Аутентификация:

1. `POST /api/permissions/auth/login/` с телом `{"username": "...", "password": "..."}` — ответ содержит токен доступа `access` и сведения о пользователе; токен обновления устанавливается в cookie `crm_refresh` (путь `/api/`, `HttpOnly`);
2. последующие запросы — с заголовком `Authorization: Bearer <access>`;
3. `POST /api/token/refresh/` (cookie передаётся браузером автоматически) — новый токен доступа и новая cookie;
4. `POST /api/permissions/auth/logout/` — отзыв токена обновления и удаление cookie.

Полное описание маршрутов, параметров и схем ответов публикуется системой в формате OpenAPI 3: `/api/schema/swagger/`. Перечень маршрутов приведён в приложении А.

## Публичный API для партнёров

Запросы выполняются по HTTPS с заголовком `X-API-Key: <ключ>`.

```
curl -H "X-API-Key: <ключ>" https://crm.example.uz/api/public/projects/

curl -X POST -H "X-API-Key: <ключ>" -H "Content-Type: application/json" \
     -d '{"full_name": "Иванов Иван", "phone_number": "+998901234567",
          "source": "INTERNET", "notes": "Интересует 2-комнатная"}' \
     https://crm.example.uz/api/public/applications/
```

# Входные и выходные данные

Входные и выходные данные программного интерфейса — объекты JSON в кодировке UTF-8; файлы передаются в запросах `multipart/form-data`. Даты — в формате ISO 8601 (`ГГГГ-ММ-ДД`, дата и время — с часовым поясом). Денежные суммы — десятичные числа в виде строки или числа с двумя знаками после запятой; валюта — отдельным полем, буквенным кодом из перечня системы (`UZS`, `USD`, `EUR`, `RUB`, `CNY`, `KZT`, `GBP`, `AED`, `TRY`). Цена объекта в публичном API сопровождается полем `price_currency` — валютой прайса проекта. Коды классификаторов — строки латиницей (документ «Описание информационного обеспечения системы», приложение Б).

Файловые входные и выходные данные: шаблоны XLSX объектов и планов (выдаются системой и принимаются обратно), шаблоны и сформированные документы DOCX, выгрузки XLSX.

## Порядок внесения изменений

1. Создать ветвь от основной ветви репозитория.
2. Внести изменения, соблюдая правила раздела 2; для изменений структуры данных — создать миграцию (`python manage.py makemigrations`), для данных — миграцию с `RunPython`.
3. Добавить или обновить автоматические тесты (`tests.py` приложения).
4. Выполнить проверки:

```
cd backend
python manage.py check
python manage.py makemigrations --check --dry-run
python manage.py test apps permissions --top-level-directory .
cd ../frontend-new
npx tsc -p tsconfig.app.json --noEmit
npm run build
```

5. Если изменилось поведение — обновить ролевые инструкции (`docs/_src/body-*.html`, затем `bash docs/_src/build.sh`) и проектную документацию (`docs/gost/src/*.md`; при изменении моделей или маршрутов — снимок `python ../docs/gost/tools/snapshot.py` из каталога `backend`; затем `python docs/gost/tools/build.py` и `tools/finalize.ps1`).
6. Передать изменения на проверку и испытания по документу «Программа и методика испытаний».

> Примечание – Команда `manage.py test` без указания `apps permissions` пытается импортировать сценарии `test_*.py` из корня каталога `backend`, которые не являются модулями тестов, и сообщает об ошибках их загрузки. Указание меток приложений исключает эти сценарии.
