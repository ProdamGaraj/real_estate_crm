# Состав информационного обеспечения

Информационное обеспечение системы включает:

- внутримашинную информационную базу — БД PostgreSQL с данными всех подсистем;
- файловое хранилище — изображения, сканы документов, шаблоны договоров;
- оперативные данные в хранилище Redis — кэш, счётчики ограничения частоты запросов и неудачных попыток входа (не являются данными длительного хранения и восстанавливаются автоматически);
- классификаторы, заданные в программе (статусы, типы, валюты, действия и области разрешений);
- справочники, ведущиеся пользователями (статусы заявок, причины отказа, точные источники, типы домов, типы платежей, счета получателей);
- файлы локализации интерфейса на русском, английском и узбекском языках;
- входные и выходные документы — шаблоны XLSX для загрузки объектов и планов, шаблоны DOCX договоров, выгрузки XLSX, сформированные договоры DOCX.

# Организация информационного обеспечения

Данные организованы по принципу единой БД для всех компаний с логической изоляцией: каждая бизнес-запись и каждая запись справочника содержит ссылку на компанию (поле `company_id`). Записи справочников без компании являются общесистемными.

Принадлежность записей сотрудникам определяется полями автора и ответственного (`created_by`, `executor`, `responsible_employee` и т.п.), принадлежность отделу — через профиль сотрудника. По этим полям строится отбор записей по области видимости разрешений.

Целостность данных обеспечивается:

- ограничениями внешних ключей с правилами удаления (каскадное удаление подчинённых записей, запрет удаления используемых записей, обнуление ссылки);
- ограничениями уникальности, в том числе составными: номер объекта в пределах дома, адрес электронной почты клиента в пределах компании, номер договора в пределах компании;
- проверками серверной части при сохранении (суммы графика, валюты, допустимые переходы статусов);
- выполнением составных изменений в одной транзакции.

История изменений хранится в таблицах журналов (суффикс `log` в имени таблицы): запись журнала содержит ссылку на изменённую запись, автора, время и описание изменения.

# Организация сбора и передачи информации

Информация поступает в систему:

- вводом пользователями через формы клиентского приложения;
- загрузкой файлов XLSX по шаблонам системы: объекты дома (функция КАТ-03), планы продаж по проектам и по сотрудникам (АНА-03);
- массовой загрузкой изображений планировок (КАТ-06);
- через публичный API от систем партнёров — заявки (ИНТ-02);
- расчётом регламентных заданий — статусы платежей, сделок, встреч (подсистема РЕГ).

Информация выдаётся из системы:

- экранными формами клиентского приложения;
- выгрузкой сводных таблиц в XLSX;
- формированием договоров DOCX по шаблонам (ДОК-02);
- через публичный API партнёрам — проекты, дома, планировки (ИНТ-01);
- выдачей файлов по подписанным ссылкам.

Передача данных между клиентским приложением и сервером, а также между сервером и партнёрами выполняется по HTTPS в формате JSON (файлы — в составе запросов `multipart/form-data`).

# Построение системы классификации и кодирования

Классификаторы, определяющие поведение системы, заданы в программе перечислениями. Значения хранятся в БД кодами латиницей (например, `BOOKING`, `IN_PROGRESS`), наименования для пользователя выводятся из файлов локализации на языке интерфейса. Перечень классификаторов приведён в приложении Б.

Справочники, ведущиеся пользователями, кодируются суррогатным числовым ключом; статусы заявок дополнительно имеют символьный код. Записи справочников принадлежат компании.

Разрешение на доступ кодируется тройкой «действие — ресурс — область» и имеет символьный код вида `VIEW_CLIENT_OWN` (просмотр клиентов, только свои записи). Перечни действий, ресурсов и областей приведены в приложении Б.

Телефонные номера клиентов приводятся к единому виду: знак «+» и только цифры; местные девятизначные номера Узбекистана и номера, начинающиеся с «8», дополняются кодом страны 998, например `+998901234567`.

Объект недвижимости идентифицируется сочетанием «дом — номер объекта»; номер уникален в пределах дома.

# Организация внутримашинной информационной базы

## Общие сведения

Внутримашинная информационная база реализована в СУБД PostgreSQL 16. Структура БД описывается моделями Django в исходных текстах серверной части и изменяется только миграциями (каталоги `migrations` приложений). Миграции применяются автоматически при запуске серверной части.

Таблицы БД разделяются на:

- прикладные таблицы системы — 42 таблицы, перечисленные в таблице 4 и описанные в приложении А;
- служебные таблицы фреймворка Django и библиотек: учётные записи пользователей (`auth_user`), группы и права Django (`auth_group`, `auth_permission` и связи), типы содержимого (`django_content_type`), журнал административного интерфейса (`django_admin_log`), сессии (`django_session`), история миграций (`django_migrations`), выданные и отозванные токены обновления (`token_blacklist_outstandingtoken`, `token_blacklist_blacklistedtoken`).

Имена прикладных таблиц образуются по правилу `{приложение}_{модель}`. Первичный ключ каждой таблицы — поле `id` типа `bigint` с автоматической нумерацией. Ссылки на учётные записи пользователей указывают на таблицу `auth_user`.

## Основные связи данных

Основные связи между данными:

- компания (`permissions_company`) — владелец отделов, профилей сотрудников, клиентов, заявок, встреч, сделок, платежей, проектов, скидок, шаблонов и записей справочников;
- проект (`realty_project`) включает дома (`realty_building`), дом — объекты (`realty_property`) и планировки (`realty_layout`); объект ссылается на планировку;
- клиент (`crm_client`) имеет телефоны (`crm_clientphonenumber`), файлы (`crm_clientfile`), заявки (`crm_application`), встречи (`crm_meeting`) и сделки (`deals_deal`);
- сделка ссылается на клиента, объект и (необязательно) заявку; имеет применённые скидки (связь «многие ко многим» с `realty_discount`) и платежи (`finances_payment`);
- платёж ссылается на сделку, клиента, тип платежа, счёт получателя и ответственного сотрудника; сумма платежа хранится в валюте сделки, у строк графика, введённых в другой валюте, — также введённая сумма, валюта и курс пересчёта;
- компания хранит валюту сделок и перечень поддерживаемых валют, проект — валюту прайса; сделка хранит цену по прайсу, её валюту и курс пересчёта на день брони;
- курс валюты (`finances_exchangerate`) — число сумов за единицу валюты на дату; запись без компании — курс ЦБ, общий для всех компаний, запись с компанией — ручной курс этой компании; на одну дату допускается один курс ЦБ и один ручной курс компании по каждой валюте;
- условие рассрочки (`finances_installmentplan`) — срок, скидка за срок и минимальный первоначальный взнос компании; на один срок в компании — одно условие;
- профиль сотрудника (`permissions_userprofile`) связывает учётную запись с компанией, отделом и ролями; роль (`permissions_role`) — с разрешениями (`permissions_permission`) и компаниями;
- задача (`tasks_task`) ссылается на постановщика, исполнителя, наблюдателей и родительскую задачу.

## Мягкое удаление и архивирование

Заявки и встречи содержат поля `is_deleted`, `deleted_at`, `deleted_by`: удаление устанавливает признак, запись скрывается из списков и отчётов и восстанавливается снятием признака. Клиенты переводятся в статус `ARCHIVED`. Профили сотрудников содержат признаки активности и удаления; учётные записи не удаляются физически, чтобы сохранить авторство записей.

## Журналы изменений

Журналы изменений хранятся в таблицах `crm_applicationlog`, `crm_clientlog`, `crm_meetinglog`, `deals_deallog`, `finances_paymentlog`, `realty_buildinglog`, `realty_discountlog`, `tasks_tasklog`, `permissions_permissionlog`. Записи журналов создаются серверной частью при изменении данных и пользователями не изменяются; удаление записей журнала задач возможно только по отдельному разрешению.

## Объём данных

Объём БД определяется числом клиентов, заявок и сделок. По оценке (без замеров на рабочих данных) одна сделка с графиком из 12 платежей и журналами занимает до 20 КБ, один клиент с заявками и встречами — до 10 КБ; при показателях технического задания (100 000 клиентов, 200 000 заявок, 20 000 сделок на компанию) объём БД одной компании составит единицы гигабайт без учёта файлов. Фактический объём контролируется по размеру резервных копий.

## Резервные копии

Резервные копии БД создаются контейнером `db-backup` в каталоге `backups` сервера: еженедельно с хранением четырёх еженедельных и трёх ежемесячных копий. Файловое хранилище копируется средствами площадки размещения. Порядок восстановления приведён в документе «Руководство системного программиста».
