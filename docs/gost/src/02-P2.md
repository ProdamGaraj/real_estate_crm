# Описание процесса деятельности

Деятельность отдела продаж, поддерживаемая системой, организована следующим образом.

Обращение клиента регистрируется заявкой — вручную менеджером (звонок, визит в офис) или автоматически, если обращение пришло с сайта или от партнёра через публичный API. Менеджер берёт заявку в работу, уточняет интересы клиента (тип недвижимости, площадь, этаж, проекты) и назначает встречу. После встречи менеджер вводит её результат.

Подбор объекта выполняется по шахматке дома: цвет ячейки показывает, свободен ли объект. Выбранный объект бронируется — создаётся сделка в статусе «Бронь», объект выводится из продажи, цена фиксируется. Менеджер согласует с клиентом стоимость по договору, применяя только утверждённые скидки, и вместе с финансистом строит график платежей; с сохранением графика сделка переходит в работу.

Специалист по оформлению проверяет данные клиента, присваивает номер и дату договора, формирует договор из шаблона, после подписания загружает скан и вводит даты подписания — сделка закрывается автоматически, а заявка, из которой она выросла, получает статус «Успешно закрыта».

Финансист ежедневно отмечает поступления по графикам. Неоплаченные в срок платежи система переводит в просроченные; при расторжении сделки полученные деньги переходят в статус «К возврату» и закрываются после фактического возврата.

Руководитель отдела контролирует воронку (забытые заявки, просроченные встречи), сделки и дебиторскую задолженность, загружает планы продаж и анализирует отчёты «план-факт». Администратор поддерживает структуру, права, справочники, каталог и шаблоны. Последовательность функций и правила их выполнения приведены в документе «Описание автоматизированных функций».

Контейнеры разделены на три сети. Сеть `frontend_network` связывает обратный прокси с клиентским приложением. Сеть `backend_network` — внутренняя: она не имеет выхода в Интернет, и в ней работают серверная часть, СУБД, Redis, служба регламентных заданий и резервное копирование. Серверная часть и служба регламентных заданий дополнительно подключены к сети `egress_network`, через которую выполняются только исходящие соединения: получение курсов валют ЦБ Узбекистана и отправка почты. Наружу открыты только порты обратного прокси; порты СУБД, Redis и серверной части наружу не публикуются.

## Решения по взаимосвязям со смежными системами

Система взаимодействует со следующими внешними системами:

- системы партнёров (сайты, боты, агентства) — через публичный API `/api/public/` по HTTPS с ключом в заголовке `X-API-Key`; партнёр получает сведения о проектах, домах и планировках и передаёт заявки (функции ИНТ-01, ИНТ-02);
- почтовый сервер — по протоколу SMTP для писем восстановления пароля; параметры задаются переменными `EMAIL_*`; при отсутствии настроек письма записываются в журнал сервера;
- ЦБ Узбекистана — по HTTPS с открытого адреса `https://cbu.uz/ru/arkhiv-kursov-valyut/json/` получаются курсы валют (раз в час регламентным заданием и по кнопке в настройках); при недоступности ЦБ действует последний загруженный курс, а курс можно ввести вручную;
- удостоверяющий центр Let's Encrypt (необязательно) — для выпуска сертификатов HTTPS.

Обмен с бухгалтерской системой автоматизированно не выполняется: данные о платежах выгружаются в Excel из сводной таблицы раздела «Финансы» и сверяются вручную.

## Решения по режимам функционирования

Штатный режим — круглосуточная работа. Регламентные задания выполняются раз в час без остановки работы пользователей. Резервное копирование БД выполняется без остановки системы (утилита `pg_dump`).

Режим обслуживания — обновление выполняется пересборкой и перезапуском контейнеров; миграции БД применяются автоматически при запуске серверной части. Порядок приведён в документе «Руководство системного программиста».

## Решения по численности, квалификации и функциям персонала

Решения соответствуют требованиям технического задания (подраздел 4.1.2). Функции пользователей разграничиваются ролями: типовыми (SYSTEM_ADMIN, COMPANY_ADMIN, DEPARTMENT_MANAGER, MANAGER, VIEWER) и пользовательскими, которые администратор создаёт для специалистов по оформлению, финансистов и других должностей.

## Обеспечение потребительских характеристик

Производительность обеспечивается:

- выборкой связанных записей одним запросом при формировании списков;
- индексами по полям отбора и сортировки (компания, статус, даты, ответственный);
- постраничной выдачей списков по запросу клиента (параметр `page`, по умолчанию 50 записей, не более 500);
- кэшированием в Redis.

Ограничение частоты запросов на уровне серверной части разделено по назначению: попытки входа — 5 в минуту с IP-адреса; работа пользователя — 300 запросов в минуту и 6 000 в час; анонимные запросы — 100 в час; партнёры — по лимитам своего ключа. Дополнительно обратный прокси ограничивает частоту обращений с одного IP-адреса к маршруту получения токена `/api/token/` (5 в секунду), к публичному API (20 в секунду) и к программному интерфейсу в целом (50 в секунду); вход через интерфейс (`/api/permissions/auth/login/`) подпадает под общее ограничение прокси и под ограничение попыток входа серверной части.

## Решения по комплексу технических средств

Система размещается на одном сервере (виртуальной машине) под ОС Linux с Docker Engine и Docker Compose. Минимальная конфигурация приведена в техническом задании (подраздел 4.3, требования к техническому обеспечению). Данные размещаются в именованных томах Docker (БД, Redis, статические файлы, журналы) и в каталогах сервера (`backend/media` — файлы, `backups` — резервные копии), что позволяет переносить и копировать их средствами ОС.

## Решения по информационному обеспечению

Данные хранятся в одной БД PostgreSQL; структура БД задаётся моделями Django и изменяется только миграциями. Файлы (изображения, сканы, шаблоны) хранятся в файловом хранилище, в БД — пути к ним. Состав данных, классификаторы и структура таблиц приведены в документе «Описание информационного обеспечения системы».

## Решения по программному обеспечению

Серверная часть реализована на Python с фреймворком Django и библиотекой Django REST framework, клиентская — на TypeScript с библиотекой React. Программный интерфейс описывается в формате OpenAPI 3 автоматически (библиотека drf-spectacular) и публикуется системой по адресам `/api/schema/swagger/` и `/api/schema/redoc/`. Состав ПО приведён в документе «Описание программного обеспечения».

## Решения по защите информации

### Аутентификация и сессии

Аутентификация выполняется по имени пользователя и паролю. После успешного входа сервер выдаёт токен доступа JWT сроком 30 минут и токен обновления сроком 1 сутки. Токен доступа клиентское приложение держит только в оперативной памяти страницы, токен обновления сервер передаёт в cookie с признаками `HttpOnly` и `SameSite=Lax` (а при работе по HTTPS — `Secure`), ограниченной путём `/api/`. Такое хранение исключает кражу токенов сценариями страницы, в отличие от хранения в `localStorage`.

Токены обновления заменяются при каждом использовании, использованные заносятся в чёрный список. При смене пароля все выданные пользователю токены обновления отзываются. Неудачные попытки входа подсчитываются в Redis; после 10 попыток вход по имени пользователя блокируется на 5 минут.

### Разграничение доступа

Модель доступа основана на разрешениях вида «действие — ресурс — область видимости». Разрешения объединяются в роли; пользователь получает объединение разрешений своих ролей. Проверка выполняется на сервере в двух местах:

- при обращении к операции — по классам разрешений программного интерфейса (проверяется наличие разрешения на действие с ресурсом);
- при выборке данных — отбором записей по области видимости (свои, отдел, компания, система).

Клиентское приложение скрывает недоступные разделы и действия, но не является средством защиты: все проверки дублируются на сервере.

### Изоляция компаний

Каждая бизнес-запись и каждая запись справочника хранит ссылку на компанию. Выборки ограничиваются компанией пользователя; при создании записи компания берётся из профиля пользователя, а не из запроса. Ссылки на записи другой компании (например, выбор чужого клиента в сделке или чужого счёта получателя в платеже) отклоняются при проверке входных данных. Уникальность адреса электронной почты клиента и номера договора обеспечивается в пределах компании, поэтому одинаковые сведения в разных компаниях не связывают их записи. Для поиска записей, оставшихся без компании, и закрепления их за компанией предусмотрена команда `check_company_isolation`.

### Защита файлов

Изображения проектов, домов, планировок и аватары общедоступны и отдаются обратным прокси напрямую. Остальные файлы (сканы паспортов, договоры, вложения) выдаются только по ссылке с цифровой подписью сервера и сроком действия (по умолчанию 1 ч): серверная часть проверяет подпись и передаёт отдачу файла обратному прокси (заголовок `X-Accel-Redirect`), который читает файл из внутреннего, недоступного снаружи пути.

### Защита публичного API

Ключ партнёра — случайная строка из 64 шестнадцатеричных знаков. В БД хранятся HMAC-хеш ключа (для поиска) и его зашифрованное значение (алгоритм Fernet, ключ шифрования выводится из секретного ключа системы); открытый ключ показывается администратору один раз. Запрос принимается только по HTTPS, только с ключом в заголовке; проверяются срок действия и активность ключа, список разрешённых IP-адресов, разрешённое действие и лимиты частоты запросов ключа.

### Журналирование

Изменения бизнес-записей фиксируются в журналах по видам записей (журналы заявок, клиентов, встреч, сделок, платежей, домов, скидок, задач) с автором и временем. Изменения ролей и прав фиксируются в журнале изменений прав с IP-адресом. События безопасности серверной части записываются в отдельный файл журнала `security.log`.

### Защита передачи данных

В промышленной эксплуатации обратный прокси принимает соединения по HTTPS; включение перенаправления с HTTP на HTTPS и заголовка HSTS управляется переменной `SECURE_SSL_REDIRECT`. Обратный прокси добавляет заголовки `X-Frame-Options`, `X-Content-Type-Options`, `X-XSS-Protection`. Приём запросов с других источников ограничен списком `CORS_ORIGINS`.

## Решения по обеспечению надёжности

Операции, изменяющие несколько записей, выполняются в одной транзакции БД: создание брони (с блокировкой записи объекта, что исключает двойную бронь при одновременных запросах), сохранение графика платежей, отмена и расторжение сделки, отметка возврата с освобождением объекта.

Удаление заявок и встреч выполняется как мягкое; клиенты переводятся в архив; записи, на которые ссылаются сделки и платежи, защищены от удаления ограничениями целостности БД и проверками сервера.

Контейнеры перезапускаются автоматически (`restart: unless-stopped`); для серверной части, СУБД, Redis, клиентского приложения и обратного прокси настроены проверки работоспособности. Серверная часть ожидает готовности СУБД и Redis перед запуском. Резервные копии БД создаются еженедельно (воскресенье, 03:00) с хранением четырёх еженедельных и трёх ежемесячных копий. Файловое хранилище в резервное копирование контейнера `db-backup` не входит и копируется средствами площадки.

## Решения по многоязычности

Все надписи интерфейса берутся из файлов локализации клиентского приложения (`ru.json`, `en.json`, `uz.json`); язык по умолчанию — русский, он же используется, если перевода нет. Коды классификаторов (статусы, типы) передаются сервером латиницей и переводятся в интерфейсе. Сообщения сервера и тексты журналов формируются на русском языке; их локализация включена в перечень развития системы.

# Мероприятия по подготовке объекта автоматизации к вводу системы в действие

Мероприятия приведены в техническом задании (раздел 8). Дополнительно до начала эксплуатации необходимо:

1. выпустить и установить сертификат HTTPS, включить `SECURE_SSL_REDIRECT` и `REFRESH_COOKIE_SECURE`;
2. задать надёжный секретный ключ системы и сохранить его в защищённом месте: от него зависят подписи ссылок на файлы, ссылки восстановления пароля и шифрование API-ключей партнёров;
3. настроить отправку почты для восстановления паролей;
4. настроить резервное копирование файлового хранилища и проверить восстановление БД из резервной копии;
5. выполнить первичную инициализацию прав доступа командой `init_permissions` и создать первого системного администратора.
